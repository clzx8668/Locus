# AI 收件箱参考卡片对齐计划

## 概述

本次计划针对 `idea_detail_page.dart` 中内嵌的 AI 收件箱卡片做全端统一重构，但以参考图的移动端待办卡片为主要视觉标尺。目标不是删除能力，而是在保留原有收件箱核心功能的前提下，把当前偏“工程表单”的结构收敛为“单卡片、低边界、强内容分组、次级信息折叠”的展示方式。

最终效果应满足：
- 视觉上尽量对齐参考图中的待办卡片块：弱边线、少层级、少碎片控件、卡片内部节奏更统一。
- 结构上严格参考“标题区 → 主体列表区 → 底部轻操作区”的布局逻辑。
- 功能上保留 AI 收件箱已有的主要能力：查看抽取结果、编辑字段、确认/拒绝/撤销/重新生成、查看分发结果、补充同步目标。
- 信息层级上采用“主区常驻、次级区折叠”的策略，避免当前卡片里同时出现多个提示框、子面板、边框块。

## 一、现状分析

### 1.1 当前主实现位置

当前 AI 收件箱主实现集中在：
- `e:\Dev\Locus\lib\features\idea_stream\presentation\pages\idea_detail_page.dart`

关键方法：
- `_buildDispatchInboxCard()`：收件箱卡片总容器与内部结构
- `_buildInboxFields()` / `_InboxFieldList`：字段列表区
- `_buildPendingActionIcons()` / `_buildConfirmedActionIcons()` / `_buildInboxActions()`：操作区
- `_buildMissingFieldsBanner()`：缺键信息横幅
- `_buildSyncTargetsCheckboxes()`：多目的地同步区域
- `_buildInboxDispatchedLinkRow()`：已分发链接行
- `_buildSupplementaryArea()`：收件箱与 AI 对话混排入口

### 1.2 当前结构特征

当前 `_buildDispatchInboxCard()` 大致结构为：
1. 外层卡片容器
2. 标题行：`AI 识别 → 意图 (状态)` + 状态图标
3. 缺键横幅（pending 且缺字段时）
4. 字段列表区（`_InboxFieldList`）
5. 分发链接区（confirmed 时）
6. 多目的地勾选区（未确认时）
7. rejected 底部按钮区

### 1.3 当前与参考图的主要差异

参考图中的待办卡片明显具备以下特征：
- 只有一个主卡片，不再套多个“子面板盒子”
- 卡片边线极弱，主要依赖背景分层与排版节奏，而不是内部边框
- 标题、摘要、列表项、底部操作是连续内容流，不是“横幅 + 字段盒 + 复选盒 + 链接盒”的堆叠
- 次要功能存在，但不打断主阅读路径

而当前收件箱卡片存在这些不一致点：
- 外层卡片内部又嵌套了字段面板、缺键横幅、多目标面板、链接行，导致层级偏多
- `_InboxFieldList` 与 `_InboxFieldChip` 使用了较明显的背景块和描边，移动端尤其碎片化
- 标题行信息偏“系统状态栏”，不够像参考图中的“业务卡片标题”
- 缺键提示与多目标同步区域都以独立盒子呈现，视觉断裂明显
- rejected 状态仍单独占一行按钮区，和其余状态的整体卡片语言不统一

### 1.4 当前可复用基础

已有基础可以复用，无需重做业务能力：
- 收件箱和 AI 对话已在 `_buildSupplementaryArea()` 中合并排序
- pending / confirmed 的图标操作已能并入字段尾部
- 字段编辑逻辑已通过 `_dispatchService.updateInboxExtractedData()` 打通
- 分发链接、缺键检测、多目的地同步能力都已可用

因此本次更适合做“信息架构与样式重组”，而不是改业务流程。

## 二、方案决策

### 2.1 已确认的产品取舍

- 适配范围：`全端统一重构`
- 信息层级：`折叠次级信息`
- 主要参照：用户提供的移动端参考图中的待办卡片块

### 2.2 本次设计决策

1. **卡片保留单一主容器**
   - 外层仍保留一个 `Container + BoxDecoration`
   - 但内部尽量移除“盒中盒”结构，减少独立背景块和边框块

2. **将标题区改为“业务卡片头”而不是“系统识别头”**
   - 保留意图类型与状态，但弱化 `AI 识别 →` 这类系统感文案
   - 改为更接近参考图的“主标题 + 次信息”布局

3. **主内容区改为纵向列表式呈现**
   - TODO/CRM/LEDGER 的识别字段不再优先展示为大量 chip
   - 优先改为“标签-值”的纵向条目列表，减少内部描边和碎片块

4. **次级信息统一折叠**
   - 缺键提示、多目的地同步、分发链接、辅助说明收进一个“次级信息区”
   - 默认折叠，仅在需要时展开
   - 展开入口放在卡片底部轻操作区或卡片头部次级行

5. **操作区统一为底部轻操作带**
   - 保留原有主要功能
   - 统一收敛为参考图那种“卡片底部轻量图标操作区”
   - pending / confirmed / rejected 三种状态共享同一布局语言，只是动作集合不同

## 三、拟修改文件与实现方式

### 3.1 `lib/features/idea_stream/presentation/pages/idea_detail_page.dart`

这是本次核心改动文件。

#### A. 重构 `_buildDispatchInboxCard()`

**要改什么**
- 重新组织当前卡片内部结构，从“标题 + 多个子块”改为：
  1. 卡片头部
  2. 主内容区
  3. 次级信息折叠区
  4. 底部操作区

**怎么改**
- 头部区域：
  - 用更简化的意图标题呈现，例如“待办事项 / 客户信息 / 记账记录”
  - 状态改为轻标签或右上角状态点/小图标，不再占据强视觉权重
  - 若存在时间、识别来源等辅助信息，降级为副标题文本
- 主内容区：
  - TODO 意图尽量做成接近参考图的纵向条目流
  - 非 TODO 意图也统一成简洁的 label-value 列表，不再优先使用强边框 chip
- 次级区：
  - 用一个可展开的“更多信息”区域承载缺键提示、多目标同步、分发链接
  - 默认收起，只在必要时展开
- 底部区：
  - 将现有各种状态动作统一收敛到底部轻操作区

**为什么这样改**
- `_buildDispatchInboxCard()` 当前承担了所有视觉分组，是最适合做结构层重排的位置
- 保留业务逻辑不动，只重排 UI 容器，可以降低回归风险

#### B. 重构 `_InboxFieldList`

**要改什么**
- 将当前 PC/Mobile 都偏“字段 chip 面板”的呈现方式，改为更接近参考卡片的列表结构

**怎么改**
- 移除或显著弱化这两层视觉：
  - `_buildPcLayout()` / `_buildMobileLayout()` 外层 `surfaceContainerHighest` 背景块
  - `_InboxFieldChip` 上的独立边框和块状背景
- 移动端：
  - 改为纵向字段行，行内是“标签 + 值 + 可编辑提示/图标”
  - “查看全部”保留，但放在主内容区尾部的文本入口，不再单独形成盒子感
- 桌面端：
  - 不再使用密集 `Wrap chip`
  - 优先改为 1~2 列信息行布局，保持更接近移动端的阅读逻辑

**为什么这样改**
- 当前碎片感主要来自 `_InboxFieldList` / `_InboxFieldChip`
- 只改外层卡片不改字段区，最终仍会保留强烈“表单感”

#### C. 改造 `_buildMissingFieldsBanner()`

**要改什么**
- 从当前显性的黄色横幅，改为折叠区中的轻提示项

**怎么改**
- 不再默认常驻为独立整行告警盒
- 若存在缺键：
  - 在卡片头部或副标题区显示一个轻量提醒（如“待补充 2 项信息”）
  - 展开折叠区后再展示具体缺失字段和补充入口

**为什么这样改**
- 黄色横幅会直接打断参考图所要求的简洁内容流

#### D. 改造 `_buildSyncTargetsCheckboxes()`

**要改什么**
- 从单独子面板改为折叠区内的次级设置模块

**怎么改**
- 保留勾选能力和当前状态管理 `_selectedSyncTargets`
- 但不再在主卡片常驻展示“同时写入”盒子
- 放进折叠区，文案与控件密度同步收敛

**为什么这样改**
- 多目的地同步是次级能力，不应抢占主阅读区

#### E. 收敛 `_buildInboxDispatchedLinkRow()`

**要改什么**
- 保留查看分发结果的入口，但从强存在感链接行改为次级信息项

**怎么改**
- confirmed 状态下，将分发结果入口放进折叠区或卡片底部次级操作位
- 避免在主内容区中间出现独立蓝色链接行，破坏卡片整体节奏

#### F. 统一操作区

**涉及方法**
- `_buildPendingActionIcons()`
- `_buildConfirmedActionIcons()`
- `_buildInboxActions()`

**要改什么**
- 统一三类状态的底部操作区布局语言

**怎么改**
- pending / confirmed / rejected 都回归“卡片底部轻操作带”
- 与参考图类似，弱化按钮边框，尽量采用图标操作 + 必要时的单一文本入口
- 保证主要功能不丢：
  - pending：重新生成 / 拒绝 / 确认
  - confirmed：编辑 / 撤销
  - rejected：编辑后重新规则化

**为什么这样改**
- 当前 rejected 状态与其余状态的操作布局不统一
- 参考图底部操作区是整体视觉完成度的重要部分

### 3.2 `lib/features/idea_stream/presentation/pages/idea_detail_page.dart` 中的状态管理补充

若采用折叠次级区，需要在 `_IdeaDetailPageState` 中新增轻量本地 UI 状态，例如：
- `Set<int> _expandedInboxSecondaryInfo = {};`

用途：
- 记录哪些 inbox 的“次级信息区”已展开

这样做的原因：
- 当前页面已存在 `_editedEntities`、`_selectedSyncTargets` 这类局部 UI 状态
- 用同一页面状态管理折叠开关最直接，且无需引入额外状态层

## 四、实施步骤

### Step 1：先重排卡片骨架
- 在 `_buildDispatchInboxCard()` 内先完成头部 / 主内容 / 次级区 / 底部区的区域拆分
- 暂时保留原子内容方法不变，只调整装配顺序

### Step 2：重做字段区视觉
- 收敛 `_InboxFieldList`
- 将移动端和桌面端统一到更接近“列表行”的模式
- 逐步弱化 `_InboxFieldChip` 的描边、块感和编辑图标存在感

### Step 3：接入次级信息折叠
- 将缺键提示、多目标同步、分发链接迁移到折叠区
- 头部只保留轻量提示摘要

### Step 4：统一底部操作区
- 三个状态统一到底部轻操作带
- 确保原有按钮回调全部复用，不改业务逻辑

### Step 5：做全端排版收尾
- 移动端优先严格对齐参考图
- 桌面端沿用相同信息架构，但允许更宽内容区和更松列宽

## 五、验收标准

### 5.1 外观验收
- AI 收件箱卡片不再出现多个明显的“盒中盒”结构
- 外边线显著减少，冗余间距减少，卡片内部视觉层级更扁平
- 整体布局逻辑可明显对应到参考图的卡片结构

### 5.2 功能验收
- 字段查看与编辑仍可用
- pending / confirmed / rejected 三种状态的主要功能都保留
- 多目的地同步、缺键信息、分发结果入口仍可访问

### 5.3 适配验收
- 移动端：优先达到参考图风格一致性
- 桌面端：保持同一信息架构与视觉语言，不出现碎裂的 PC 专属样式
- 补充区域混排（收件箱 + AI 对话）顺序不变

### 5.4 工程验收
- `idea_detail_page.dart` 无新增诊断错误
- 不引入 UI 层直接访问数据库的新路径
- 不回退已有已完成 spec 中的按钮图标化与功能行为

## 六、假设与边界

### 6.1 已采用的假设
- 参考图主要约束的是“卡片结构与视觉层级”，不是要求把 AI 收件箱完全改造成真正的待办组件
- “保留主要功能”意味着功能入口可以收敛、折叠或换位，但不能删除能力
- 本次不重做收件箱与 AI 对话的混排策略，不改 `_buildSupplementaryArea()` 的排序逻辑

### 6.2 不在本次计划内
- 不改收件箱数据结构、状态机、分发表逻辑
- 不改 `DispatchService` / `Repository` / `database.dart`
- 不新增独立页面或新的全局状态管理方案

## 七、验证步骤

实施完成后按以下顺序验证：

1. 代码验证
   - 检查 `idea_detail_page.dart` 的诊断结果

2. 视觉验证
   - 对比参考图，确认：
     - 卡片边界减弱
     - 内部间距更紧凑
     - 字段区不再呈现明显表单块
     - 底部操作区与整体卡片更统一

3. 功能验证
   - pending 状态：重新生成 / 拒绝 / 确认
   - confirmed 状态：编辑 / 撤销
   - rejected 状态：编辑后重新规则化
   - 查看全部、字段编辑、分发链接、多目标同步、缺键提示仍可触达

4. 断点验证
   - 手机窄屏
   - 平板/横屏中宽度
   - 桌面宽屏

5. 风格一致性验证
   - 与参考图比对卡片结构逻辑是否一致
   - 与页面内现有内容块并排时，是否依然保持统一且不过度突兀
